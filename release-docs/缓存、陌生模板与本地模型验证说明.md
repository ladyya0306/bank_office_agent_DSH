# 缓存、陌生模板和换电脑：怎样判断效果

核对日期：2026-09-27。本轮核对代码、既有测试和test B会话用量；没有清除业务数据，没有重新执行真实填表，也没有在另一电脑或本地小模型上完成实测。下文测试方案均为待执行。

## 1. 两种缓存不要混在一起

| 名称 | 保存什么、在哪里 | 换电脑怎么处理 |
|---|---|---|
| 模型服务的输入缓存 | 服务端复用已经计算过的相同输入开头，例如系统说明、工具说明和前面的对话；日志里的cacheReadTokens属于这一类 | 不在DSH程序文件夹中，不随安装包搬走；新电脑若连接同一服务，仍可能获得服务端缓存；离线本地模型须自行建立其计算缓存 |
| toolV2的业务保存记录 | 本机业务目录的db/workflow.db保存来源解析结果、规则、确认答案和任务进度，out保存文件 | 干净首装不带旧业务目录和DSH旧会话；继续旧业务才按范围迁移。不要为了测试删掉日常数据库 |

DeepSeek官方说明：重复输入开头可以命中缓存，但输出仍经过计算生成；缓存并不直接提供预先存好的答案。服务自动管理和清理缓存。它通常减少重复输入的处理成本和等待，不等于给模型额外增加解题能力。[官方说明](https://api-docs.deepseek.com/guides/kv_cache/)

例如第一次让模型读资料，第二次工具返回“找到3个位置”。第二次请求通常还包含前面的说明和对话，其中相同部分可以复用。因此，**一项全新的业务在执行过程中也会自然产生缓存**；不是只有“昨晚做过同一道题”才有缓存。

本机换目录、新建会话或删数据库，都不能证明远端服务缓存已清空。当前维护流程没有远端缓存清除功能；测不到全程零命中时，就报告真实命中数，不把它称为完全无缓存测试。也不建议靠反复删除日常记录来追求零缓存。

## 2. test B究竟证明了什么

北京时间2026-09-27 01:04:34.741—01:07:12.070，157.329秒；15份新生成，0份旧产物复用。日志累计：

| 项目 | 数值 |
|---|---:|
| 缓存读取 | 1,490,304 token |
| 未命中缓存的输入 | 95,522 token |
| 输出 | 22,313 token |
| 总计 | 1,608,139 token |
| 带用量记录的助手消息 | 26条 |
| 单次输入最大值，含缓存输入 | 115,792 token |
| office_fill_task调用 | 44次 |

上述用量来自DSH会话字段；逐条检查满足“总计=非缓存输入+缓存输入+输出”。累计160.8万不表示一次输入了160.8万，更不表示模型生成了160.8万字。同一段历史在多次请求中出现，会被多次计入累计用量。

**判断应分开：**有缓存帮助速度；15份文件确实新生成；但“新生成15份”不证明没有使用已存填写规则或确认答案。现有摘要没有逐项记录这些命中情况，本次不能据此认定test B是业务记录完全空白的测试。157.329秒也不能直接拿来预测零缓存耗时；没有对照实测，不能计算慢几倍。

少了输入缓存，通常需要重新计算重复输入，成本或耗时会增加；不能因此断言业务推理必然变差。同样，保留输入缓存也不会让新模板自动获得正确映射。

## 3. 改来源内容或改模板格式，会发生什么

当前程序依据文件实际内容计算识别值，不只看文件名。具体行为来自toolV2的source.py、runner.py及fill_decisions.py：

| 改动 | 当前处理 | 对效果的含义 |
|---|---|---|
| 来源金额从100万元变成200万元 | 文件内容变化，重新解析变化来源；相关值及证据改变后，不沿用不匹配的旧确认 | 应采用新值；相关输出需要重新处理，耗时可能增加 |
| 模板增加一行、移动填写格、改变合并格 | 模板识别值变化，重新检查位置、生成计划；旧产物不能仅凭同名复用 | 新布局是否识别正确须验证，可能需要重新映射或提问 |
| 只改字体或页边距，文件字节变化 | 当前也会触发模板变化检查；填报确认指纹包含整个模板内容 | 可能重新处理和再次确认，即使业务含义没变；当前没有证明所有纯排版变化都能免问 |
| 材料、规则、批次及产物均未变化 | 在核验条件相同后复用已有工作 | 这是正常减少重复计算，不是必须删除的“作弊答案” |

已有合成测试包含：来源电话/账号改变后重问；两模板中只改一份，生成1份、复用1份；候选值从100改成200后不继承旧留空回答。本轮只核对这些测试代码，没有重跑；它们也不能证明所有陌生版式均能正确解析。

注意保存并关闭编辑中的Word/Excel，再让任务检查变化；否则磁盘上可能还是旧内容。上述描述针对本仓库当前toolV2，不等于另一项目规划的“固定输入快照”机制。

## 4. 怎样验证陌生模板，而不是继续做熟题

目标是证明某个明确范围内的稳定表现，不能用有限测试证明所有可能文档都一样好。下面是建议的首轮方法，不是已经取得的结果，也不是新加的运行拦截规则。

1. **先固定程序版本。** 记录代码版本、模型、模型设置和电脑配置，测试过程中不改程序。
2. **准备没有参与开发的模板。** 由独立出题者提供多个来源的Word/Excel版式，配合合成企业资料。不要只把旧题的公司名字换掉；应有位置移动、跨页表格、合并格、标签不同、保证人顺序不同、资料缺失或冲突等情况。
3. **答案单独保存。** 执行填报的模型只能看到来源和空白模板，不能访问参考答案；运行结束后由独立检查者核对。
4. **第一次使用新的业务目录和新会话。** 目录里只放source和target，不复制旧db、work、out和DSH会话。这样可以验证没有预存业务答案的表现；不声称模型服务缓存也归零。
5. **分别测三种使用情况。** 第一次填报；原样再次请求；改来源内容或模板后再次请求。分别统计，不把再次请求的速度冒充首次速度。
6. **每批至少重复3次，保留全部失败。** 初步可用3批、每批10份不同模板；这是建议起点，不能代表统计上已经充分。每次首次测试另建干净业务目录；同批的第二、三种情况保留该次状态。
7. **先看正确，再看速度。** 逐位置记录应填、正确、错填、漏填、应该留空；单列主体串位、单位错误、排版破坏、无依据编造。另记必要/重复提问、问题是否说清主体、失败恢复、重复执行、模型调用数、总token/缓存token和总耗时。报告中位数和最慢值，不只展示最快一次。

例如100个有依据的应填位置中95个正确、3个错填、2个漏填，应报告“95/100”，不能只统计已经填上的98个。缺资料而正确留空应另计，不混成漏填。能不能启用要事先约定关键错误和人工复核要求，不在看到成绩后移动标准。

若测试发现错误并修改程序，修复后的同一道题可以作为旧功能检查，但不能继续称为未见过的新题；再用另一批未参与修复的模板验证。

## 5. 怎样验证换电脑也能用

分两步，避免把“换电脑”和“换模型”同时改变：

- **先验证安装是否完整。** 在另一台同类系统电脑或干净环境，用固定程序版本、匹配依赖、新业务目录和合成材料测试。若环境获准使用同一模型，先保持模型不变，对比原电脑。系统/平台不同还要分别验证，不能拿Windows结果证明UOS兼容。
- **再验证离线小模型。** 在获准目标电脑上断开外网，用指定本地模型跑同一组与陌生组，记录模型文件版本、量化方式、可用内存、输入长度、速度及错误；不能把原云端模型的成绩当成小模型成绩。办公机不允许公网模型时，直接进行此项，不为做对照开通公网。

安装包不带旧客户业务数据库和会话。测试使用另建的合成资料目录；原电脑的历史业务保留，不需要删除。要声称“离线可用”，必须在目标配置上实际验证模型、工具、文件输出和失败恢复，不能只验证安装脚本成功。

## 6. 本地小模型能否完成test B

我的工程判断是：单个字段的抽取、金额换算或简单对应通常属于较轻的任务；把多个主体、15份模板、缺失/冲突处理和多轮工具调用连续做好，则对上下文理解和执行稳定性要求较高。这是任务分析，不是经模型对照测出的难度等级。此前记录的High是模型设置，不是这道任务被认证为“高难度”。

更直接的限制是输入长度：test B日志最高单次输入115,792 token。此前另一项目2026-09-16的试验计划锁定Qwen3-4B-Instruct-2507 Q4_K_M、4096-token窗口，还要给输出留空间。不能把原会话原样塞进这个窗口。两种模型的分词不同，所以不把两个数字当精确等价的容量比，但差距足以说明需要重新组织输入。累计160.8万token也不能当作所需窗口大小。

这不等于所有4B模型都做不了办公任务，也不等于把窗口调大就解决了质量和内存。当前没有这个小模型完成test B同等流程的实测证据，不能承诺能完成或达到2分37秒。

合理的下一步是让程序保管完整资料和进度，每次只给小模型当前文件、当前主体及有关证据，让模型作有限选择；先验证单表和少量工具调用，再扩大到15份。工具V2已有数据库与分页等基础，可在其上检查、补齐输入长度控制，不必另造填表引擎。这仍是待验证的改进路线，不是已经完成的“小模型适配”。

本轮证据来源：本机test B会话的用量及工具计数；toolV2/workflow/source.py、runner.py、review.py、office_kit/fill_decisions.py；tests/test_workflow.py、test_source_duplicates.py、test_workflow_robustness.py、test_automatic_review.py。本地模型数字来自另一个项目的docs/24_LOCAL_MODEL_RUNBOOK.md及specs/local-model-lock.v2.json（2026-09-16计划记录），不是目标办公机本轮实测。
