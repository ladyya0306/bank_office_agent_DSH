# 部署与查看

## 当前电脑

已验收的程序在 `D:\DSH`。日常从 `deepseek-harness-local` 运行 `npm start`。本次保存版本不更换模型、不改业务数据，也不要求重新确认原有未变化的答案。

## 从 GitHub 取得源码后的准备

仓库只含源码，不能在无依赖的办公电脑上直接双击运行。先在获准环境准备 Node、Python 及相应依赖。验收环境的精确版本见 `accepted-environment.json`：本机 Node 为 v22.18.0，但 package.json 声明最低 22.19.0；这个差异如实保留，目标电脑应另验证，不在此声称已经兼容。

联网准备电脑可按以下顺序操作；办公机断网时需要提前下载相同平台的依赖包，或使用经过验证的完整离线环境，不在办公机运行在线安装命令：

```powershell
git clone https://github.com/ladyya0306/bank_office_agent_DSH.git
cd bank_office_agent_DSH
python -m pip install -r toolV2/requirements-core.txt
cd deepseek-harness-local
npm ci
cd ..
python scripts/prepare_checkout.py
```

`prepare_checkout.py` 只创建缺少的本地配置并调用原接入程序，不覆盖已有 `.env` 或读取凭据。初次使用按获准模型配置 DSH。仓库的 `.env.example` 仅为示例，不能将办公机接入未获准公网模型；本地小模型的实际能力需另验证。设置好后：

```powershell
cd deepseek-harness-local
npm start
```

新会话选择本次业务文件夹，确认办公工作区。需要工具批准框时使用 `/permission workspace-write`；不要把“完全访问”当作已经取得用户批准。本机验证不能代替新终端验证。

## 查看数据库，不修改它

数据库在 **业务工作区\db\workflow.db**，不在安装目录中。以下以合成工作区 `D:\办公示例\甲公司` 为例，在仓库根目录运行：

```powershell
python scripts/read_office_db.py --work "D:\办公示例\甲公司" --section tasks
python scripts/read_office_db.py --work "D:\办公示例\甲公司" --section facts --limit 10
python scripts/read_office_db.py --work "D:\办公示例\甲公司" --section answers --limit 10
python scripts/read_office_db.py --work "D:\办公示例\甲公司" --section outputs --limit 10
```

`tasks` 是任务状态，`facts` 是来源事实，`answers` 是填写确认，`outputs` 是填写操作及产物记录。另有 `rules`（填写位置规则）和 `events`（数据库处理事件）。程序以 SQLite 只读模式打开，不会创建缺失数据库或修改现有记录。输出可能包含客户资料，仅在本地查看，不要贴到公开论坛或 GitHub。

不要手动编辑数据库来改变答案。应在业务流程中明确提出更正，让程序保存变更；尚未实现的更正操作由维护人员处理，不能声称一句话已自动改库。

## 查看批准日志

先在 DSH 原会话中查看工具调用、批准卡及结果。磁盘上的会话日志通常在：

```text
deepseek-harness-local/workspace/sessions/<工作区对应目录>/<会话编号>/session.v3.jsonl.zstd
```

这是压缩文件，记事本不能直接阅读。沿用项目已有的只读查看器：

```powershell
node scripts/show_approvals.mjs --list
node scripts/show_approvals.mjs --session "完整会话目录或日志文件路径"
node scripts/show_approvals.mjs --session "完整路径" --types
```

查看器用于提取记录中的批准相关事件，不是完整的业务审计平台，也不能证明日志不可篡改。填写确认的详细记录还应对照办公数据库 `fill_decision` 与任务记录。文件输出报告在业务工作区 `out\批次\_报告`。判断一次动作是否执行，要把请求、决定、工具结果一起看，不能仅凭“允许”二字判断已成功。

## 回退与升级

保留当前验收标签。试验改动应在独立工作树进行，验证后才更新日常运行目录；不要在日常工作目录执行 `git clean` 或删除整个 workspace。程序回退不等于业务数据库回退。任何升级先保持数据库向后兼容，若要迁移，另行备份和说明。

业务用户可以通过会话提出“这里为什么重复问”“这个空位应属于谁”等意见。下一步计划把意见变成可复核改动、必要测试和明确启用步骤；当前并未实现无需维护人员参与的全自动自升级。
