# DSH与toolV2完整使用、维护、升级和离线部署说明

核对日期：2026-09-27。本文件替换此前不完整的“升级提示词”。先解释电脑上的实际目录，再讲怎么操作；最后才是可复制给DSH的任务文字。

只想知道怎样提出修改、怎样用上新版，直接读第5节；它按你的操作顺序写，不要求你先懂程序术语。缓存、换模板及换电脑的验证方法另见[缓存与验证说明](缓存、陌生模板与本地模型验证说明.md)。

先分清三个名字：**DSH是承载对话、模型和工具的应用；模型负责理解需求和不明确的字段关系；toolV2是DSH调用的办公填报工具流程。** 更新toolV2、升级DSH依赖、切换模型是三种不同变更，应分别验证。DSH可以协助修改toolV2，但普通填表会话不会自动升级共享程序。

## 1. 先回答最重要的四个问题

**你一直使用的是运行目录`D:\DSH`。** 在`D:\DSH\deepseek-harness-local`执行`npm start`，启动这个目录中的DSH，并接入它旁边的`D:\DSH\toolV2`。日常启动命令不用改。

**`D:\DSH-worktrees\fill-efficiency`是为修改程序另开的开发工作目录。** 当时为避免边修改边影响日常填表，维护代理创建了它；此前没有把这件事解释清楚。它不是另一套必须随产品安装的软件，也不是你测试时偷偷调用的替代引擎。

**开发目录的修改不会自动同步到运行目录。** 上轮是在开发目录完成修复和检查，再把通过检查的程序文件复制到`D:\DSH`并重新接入。你随后测试的是运行目录里已经更新的程序。这就是“在开发目录改过”与“你在运行目录使用”同时成立的原因。

**离线部署不带开发工作树，也不能把整个`D:\DSH`直接压缩交付。** 应按选定Git版本导出干净程序，补齐目标电脑适用的运行时、依赖和模型配置，做成离线发布包。包中不混入客户材料、数据库、旧会话或个人凭据。第7节给出具体组成。

## 3. 目录和文件分别负责什么

### 3.1 日常运行和业务资料

| 目录或文件 | 职责 | 日常如何处理 |
|---|---|---|
| `D:\DSH` | 本机程序安装与运行的总目录；历史上同时也是Git主工作目录 | 日常从这里启动，不把整个目录当作干净发布包 |
| `deepseek-harness-local/start.js` | 启动DSH、检查toolV2接入、输出启动日志 | 已验证升级才更换，不用于存业务资料 |
| `deepseek-harness-local/tool-v2-startup.cjs` | 找同级toolV2，调用它的接入程序 | 决定启动时寻找哪套toolV2 |
| `deepseek-harness-local/node_modules` | DSH及Node第三方依赖 | Git不保存；离线包需要另行准备兼容版本 |
| `deepseek-harness-local/package.json`、`package-lock.json` | 程序启动命令和依赖版本记录 | 不是依赖文件本身；离线机不能只靠它们安装 |
| `deepseek-harness-local/.env` | 本机运行及模型配置，可能含密钥 | 每台机器分别配置，不上传GitHub，不照搬个人凭据 |
| `deepseek-harness-local/workspace/profiles/web`、`hooks.json` | DSH工具、插件及Python路径的接入配置 | 移机或换候选版后使用现有接入程序核对，不凭记忆修改路径 |
| `workspace/plugins` | 批准、目录选择、填表等DSH插件 | 部分是版本化程序，部分由接入脚本生成；不能把整个workspace当依赖复制 |
| `workspace/skills/office-suite` | DSH实际加载的办公技能副本 | 原始技能在toolV2目录；只改这里可能被下次接入覆盖 |
| `workspace/sessions` | DSH对话、工具调用和交互记录 | 本地追查，不放公开Git或新机器的干净首装包 |
| `workspace/backups` | 接入脚本对旧配置、插件、技能的备份 | 不是完整程序备份，也不是业务数据库备份 |
| `deepseek-harness-local/logs` | 启动器运行日志；旧根目录日志也已归档到这里 | 不与业务数据库或会话记录混为一谈 |
| `D:\DSH\toolV2` | 当前运行的资料解析、任务处理及Word/Excel填报程序 | 日常使用这一份；维护通过后才更新 |
| `D:\DSH\test B`，以及test A、test3等 | 独立业务或测试工作区 | 不是程序版本；切换业务目录不会自动切换引擎 |

表中`workspace/...`均指`D:\DSH\deepseek-harness-local\workspace/...`。这里的DSH配置目录，与装有source/target/db的“业务工作区”不是同一个目录。

根目录还有一些历史和辅助材料，保留它们不意味着运行时正在调用它们：

| 目录 | 如何理解和处理 |
|---|---|
| `scripts` | 配置准备、数据库/批准记录查看等维护脚本，按固定版本交付 |
| `release-docs` | 本说明、版本状态、运行环境及查看方法；先从这里查当前事实 |
| `tool` | 旧版办公能力；toolV2是在已有引擎基础上演进，当前启动路径使用toolV2；不删旧版历史 |
| `reference`、`project_bank_adjust` | 设计参考和历史项目材料；不把其中的方案当作当前已实现功能 |
| `bank_rules` | 规则材料目录，存在rules.txt；目录本身不证明某规则已接入当前流程，修改前须查实际调用 |
| `example`、`test_answer` | 样例或核对材料，不能作为公开安装包默认内容，更不能把答案接入填表来源 |
| `audit_work` | 本机维护核查材料，不属于干净程序发布包 |

以上是本轮观察到的目录用途和维护处理方式，不建议为追求整洁直接删除历史材料。真正需要给其他电脑的文件，应以固定版本的发布清单为准。

## 5. 以后怎样让DSH修改功能：你按什么顺序做

你不需要自己找程序文件、复制整个文件夹或猜参数。**你负责说清需求、查看结果、决定启用；DSH负责改程序、测试、备份、列出要替换的文件，并准备启用和恢复旧版的方法。** 如果当前模型或工具不能完成某一步，它必须说明缺少什么，不能让你以为“修改好了”就等于“日常已经能用了”。

### 第一步：照常打开DSH，然后另开一个维护会话

仍在PowerShell执行原来的两行：

```powershell
cd D:\DSH\deepseek-harness-local
npm start
```

网页打开后，新建一个会话，选择目录`D:\DSH-worktrees\fill-efficiency`。这个会话用来改程序。平常填写材料的会话仍选你的业务目录，例如`D:\DSH\test B`。

这里“维护会话”不是新软件，只是用途不同的新对话。选开发目录的目的是让DSH找到要修改的代码。**它不会让正在运行的填表工具自动变成新版。**

### 第二步：把下面这段发给DSH，再补一句你的需求

```text
我要修改DSH的toolV2程序，不是让你完成一次普通填表。
请先读release-docs/maintenance-state.md、toolV2/MAINTENANCE.md和本仓库的AGENTS.md；涉及安装或启用时再读release-docs/交给DSH的升级提示词.md，不要重复读取全部历史材料。

日常使用的程序在D:\DSH；你在D:\DSH-worktrees\fill-efficiency修改和测试。保留旧版本和我的业务数据，不要直接覆盖正在运行的程序。

我的需求是：<用自己的话描述希望发生什么，并给一个例子>。
成功标准是：<我怎样检查结果，例如每家企业只得到自己的文件，金额不能串到其他企业>。

请完成修改，并同时检查以前能做的工作是否仍然正常。测试时请确认用的确实是你刚改的程序，不是日常旧版。能从资料确定的事不要重复问我。

我授权本次范围内的修改、合成资料测试、本地Git保存和向现有GitHub仓库的功能分支推送；不要上传客户资料、密钥或会话。测试通过后，准备这次修改专用的启用步骤和恢复旧版步骤，再向我展示结果。此阶段先不替换日常程序。

最后告诉我：改了什么、怎样证明有效、旧功能检查结果、保存的版本、是否已经启用，以及接下来我需要做的具体动作。不要只给我术语或让我自行猜该复制哪些文件。
```

例如需求可以写：“来源是一张企业明细表。希望同一份模板按企业各生成一份文件，每份只能出现对应企业的信息。”这只是说明目标；目前300家企业批量生成仍是待开发功能，不能当作已有功能直接承诺。

### 第三步：让DSH给你看新版的测试结果

DSH应先在开发目录改好、检查好。如果需要在网页里试用新版，它负责准备另一份供测试的DSH，并给你明确的打开地址，例如`http://127.0.0.1:3081`。你按它给的地址打开即可；日常地址和程序先保持原样。

你应看到具体比较，例如“旧版遇到两家公司会混填；新版生成两份文件，名称、金额分别对应；原来的多份表填写测试仍通过”。不要只接受“测试成功”四个字。

不用每次都让模型把所有测试再跑一遍。例如只改帮助文字，检查文字就够；如果改的是所有表都会用到的读取、确认或写文件程序，就要把整套已有测试重新检查，防止修好一处、弄坏另一处。DSH负责判断和执行，你不用记测试命令。

### 第四步：你决定启用后，明确说这句话

```text
测试结果我已看过。请把这次通过测试的版本启用到D:\DSH，保留我的原启动方式、模型配置、业务资料和历史结果。先备份会被替换的程序，给出备份位置和恢复方法，再更新实际需要变化的程序文件，并检查DSH确实在使用新版。
如果必须先关闭当前DSH，请先把本次专用的更新脚本、恢复脚本和说明保存好，给我真实文件路径及可直接复制的命令，再让我关闭。不要在停止自己以后才准备剩下的工作。
```

如果你在第二步已经授权“验证通过后直接启用”，无需再说一遍；DSH应继续完成，不能反复索取相同许可。

### 第五步：新版究竟怎样进入你日常使用的程序

实际动作是：**把开发目录里这次确实修改过、且测试通过的程序文件，更新到`D:\DSH`的对应位置；如果新增第三方程序包，再补装匹配版本；最后让DSH重新读取这些程序。** 不是把整个开发目录拖进D:\DSH，也不是只改一个参数就算升级。

这部分由DSH准备和执行，文件清单随本次修改而定，不能用一条“全目录覆盖”命令代替。一般分两种情况：

| 情况 | 你实际需要做什么 |
|---|---|
| 维护工具在另一独立进程中运行，关闭日常DSH后它仍能工作 | 按说明关闭日常DSH，让维护工具更新、检查，再按原命令启动 |
| 正是日常DSH里的模型在给自己升级 | 先取得DSH已保存好的更新/恢复脚本和完整说明；退出DSH后，在PowerShell运行它给的本次更新命令；成功后再启动 |

第二种情况中，如果DSH由当前PowerShell前台运行，通常在那个启动窗口按Ctrl+C退出；只关浏览器标签不等于停止后台程序。如果还有后台进程，由维护工具定位本次DSH进程并给出步骤，不让你结束所有Node进程。

更新脚本应完成：检查目标路径和文件→备份→替换本次文件→用现有安装脚本更新工具位置→报告成功或具体失败，并附恢复旧版的命令。**当前项目还没有通用的一键升级器。这里要求DSH针对实际改动准备脚本；本轮只是改说明，没有生成某个尚不存在的新功能更新包。** 你只运行DSH真正交付、说明清楚的脚本，不需要自己拼接复制命令。

完成后仍用：

```powershell
cd D:\DSH\deepseek-harness-local
npm start
```

再开一个新的合成资料测试会话，试一次新增功能和一项原功能。DSH应报告“已更新到哪个版本、实际使用哪个目录、验证结果、旧版备份在哪”，这时才算日常启用完成。只说“代码已提交GitHub”还没有完成启用。

### 第六步：如果新版有问题

先保留问题结果，不删业务数据库。停止新版DSH，按这次交付的恢复说明恢复旧程序和对应环境，再按原命令启动。如果更新改动了业务数据库的结构，DSH必须在启用前就准备数据恢复办法，不能出问题后随意拿旧数据库覆盖新增记录。

| 原来的说法 | 直白解释 |
|---|---|
| 候选DSH | 还没替换日常版本、专门给你试新版的那一份DSH |
| 接入配置 | 告诉DSH“填表工具在哪、用哪个Python启动”的本机设置 |
| toolRoot | 设置中记录的“toolV2文件夹位置”；日常应是D:\DSH\toolV2 |
| 兼容依赖 | 程序需要的第三方软件包，版本和电脑系统必须配得上 |
| node_modules | 存放DSH所需第三方软件包的文件夹；源码版本记录通常不包含它 |
| 新工作树不自带依赖 | 复制出一份开发源码，不等于Python、DSH所需软件包也跟着装好了；这是DSH维护时要检查的事 |
| 跑全量测试 | 把项目已有的整套测试都检查一遍，不只是试刚改的功能 |
| 模块化修改 | 尽量只改负责这个功能的部分；共用部分改动仍可能影响其他功能，所以要检查旧功能 |

可以理解为分部分维修，但**现有程序并不是所有功能都能随意插拔、互不影响**。模型、DSH、toolV2和第三方软件包之间仍有配合关系。

给维护模型的补充：新开发目录先检查依赖与模型配置，用相应Python执行`scripts/prepare_checkout.py`准备缺失设置；不要只运行npm start。测试新版前检查实际toolRoot，不能只改会话目录。操作细节见本文件第6、7节和`toolV2/MAINTENANCE.md`。

## 6. 本地升级和回退怎样做

本机路径保持`D:\DSH`即可，不用改你平时的启动习惯。

1. 记录已通过测试的Git提交、改动文件和依赖变化；确认没有正在执行的填表任务。
2. 保存受影响运行程序、接入配置、插件/技能的备份及文件清单。涉及数据库结构变化时，另做一致性数据库备份和迁移方案；代码备份不能代替数据库备份。
3. 退出旧DSH进程。只更新本次批准的程序和必要依赖，不把开发数据库、个人.env、会话或客户材料复制进去。
4. 用目标运行环境的Python执行运行目录中的接入程序，核对返回`tool_root`及Python路径，再按原命令启动。
5. 先跑独立合成工作区验证，再交付业务使用。记录实际启用提交、文件校验值、时间及备份位置。

接入命令示例，`python`必须指向本机实际可用且装好办公依赖的解释器：

```powershell
python D:\DSH\toolV2\install.py --dsh-root D:\DSH\deepseek-harness-local
```

**回退不是清库。** 停止新进程后，恢复上一个版本的程序、匹配依赖与接入配置，核对路径后启动。保留业务原件、数据库和产物。若数据库已经迁移，新旧代码是否兼容必须先判断；不兼容时按事先准备的数据恢复方案处理，不能直接拿旧库覆盖今天新增的业务记录。

Git标签能找到旧源码，但不会替你恢复运行目录、node_modules、Python库或数据库。`install.py`会备份部分接入配置，尚未实现失败后自动回滚。当前也没有一键离线发布、升级和数据库回退工具，不把上述人工维护步骤说成现成功能。

## 7. 离线安装包到底取哪里、装什么

### 7.1 打包来源

**源码取选定Git提交或标签；运行依赖从已经验证的环境准备，并匹配目标电脑。** 本机`D:\DSH`用于核对“好成绩所用程序”和依赖，不作为可整包公开分发的材料目录。开发工作树用于导出干净源码，不作为另一台电脑的运行依赖。

不复制`D:\DSH-worktrees`，不复制其中指回本机的`.git`文件，也不把`D:\DSH\.git`放进面向业务使用者的安装包。目标电脑正常使用DSH不要求装Git，更不要求能访问GitHub。

例如，在有该标签的开发仓库导出固定源码（先创建下面的输出目录；这是制作包时的命令，本轮未执行打包）：

```powershell
git -C D:\DSH-worktrees\fill-efficiency archive --format=zip --output=D:\DSH-release\toolv2-guide-plain-20260927-source.zip toolv2-guide-plain-20260927
```

这个ZIP只含Git保存的文件，不含node_modules、Python或模型；继续补齐下表内容并验证后，才是可交付的离线包。如此取到的是明确版本，而不是开发树里尚未提交的试验改动。

### 7.2 一个完整首装包应包含什么

以下是发布包规划，**目前尚未制作并在目标办公机验收这样的完整离线包**。

| 组成 | 内容 |
|---|---|
| 程序 | 固定版本的toolV2、DSH启动器、已跟踪的本地插件、技能源、准备/接入脚本和说明 |
| Node运行环境 | 经目标系统验证的Node安装包或运行时，以及该平台适用的DSH/node_modules依赖 |
| Python运行环境 | 经目标系统验证的Python安装包、核心依赖及其依赖包；通常准备离线wheel包集合 |
| 可选能力依赖 | 实际启用的PDF、OCR等能力所需库与资源，单独列明；安装了不代表已经验收 |
| 模型 | 目标机允许的本地模型运行时、权重与配置，或获准内网服务配置；不是复制个人API密钥 |
| 发布证据 | Git提交/标签、平台与架构、运行时/依赖/模型版本、文件SHA-256清单、合成样例及验证结果、安装和回退步骤 |

本机的Python当前来自Windows用户目录中的安装环境，不能把`D:\DSH`压缩就认为Python也已带走；现有虚拟环境也不宜原样跨机搬运。requirements文件是版本声明，不是离线依赖包。`install.py`只检查/接入，不替你安装这些依赖。

Node版本也有待发布前统一的事项：历史实测记录为22.18.0，而package.json声明至少22.19.0。应选择并验证满足项目要求的固定版本，不能把这个差异略过或笼统“下载最新版”。Windows和UOS/Linux、不同CPU架构的运行时及二进制依赖应分别准备；不要把Windows的node_modules或Python轮子直接当UOS包。

### 7.3 明确排除的内容

不打包本机`.env`、密钥、客户source/target/in/out、业务db、DSH会话、日志、备份、audit_work、test A/test B/test3、个人工作区状态。需要延续旧业务时，另做批准的数据迁移包，不能混进程序首装包。

`workspace`不能全部复制或全部丢弃：版本化插件是程序，需要随版本提供；profiles/hooks可由`prepare_checkout.py`和`install.py`生成接入；sessions、日志、运行状态和凭据属于本机数据。`office-tool-v2`插件和办公技能副本可从toolV2源目录重建；已禁用的旧插件不应被当作新包的隐含依赖。

### 7.4 首次部署到另一台电脑

在获准准备环境锁定平台、版本、依赖、模型，形成完整包；用断网的干净环境验证后再转入目标电脑。目标上建议仍保持如下普通目录关系，盘符可以改，但二者应同级：

```text
安装根目录/
  toolV2/
  deepseek-harness-local/
    node_modules/
    workspace/       # 本机生成配置；包含随版本交付的插件
  scripts/
  release-docs/
```

业务资料目录由用户另选，不必放在安装根目录；不能假设换了电脑仍存在原来的C盘用户路径。

下面是Windows离线首装的操作示例，假设批准包位于`E:\DSH-offline`、程序已放到`D:\DSH`，兼容的Node/Python已安装且PATH已核对。E盘只是示例，不是本机已制作好的包：

```powershell
python -m venv D:\DSH\.venv
& D:\DSH\.venv\Scripts\python.exe -m pip install --no-index --find-links E:\DSH-offline\wheels -r D:\DSH\toolV2\requirements-core.txt
& D:\DSH\.venv\Scripts\python.exe D:\DSH\scripts\prepare_checkout.py
$env:DSH_OFFICE_PYTHON='D:\DSH\.venv\Scripts\python.exe'
cd D:\DSH\deepseek-harness-local
npm start
```

运行前应已放入验证过的Node依赖，并按目标电脑规定配置模型。.env中的Python路径也可按本机位置设置，以便以后开新终端仍使用正确解释器。`prepare_checkout.py`只建立缺少的接入配置，不替你下载依赖或配置模型；`install.py`更新已知接入路径，并非通用修复所有自定义绝对路径。

办公机不能访问模型API时，需要实际配通并测试获准的本地模型。**程序文件能离线安装，不等于整套智能填报已经离线可用，也不等于本地小模型与这次DeepSeek Flash的速度和效果相同。** 本轮未完成目标办公机的断网验收。

## 8. 后续怎样离线升级行内电脑

开发机维护并测试→本地Git提交→推送获准GitHub分支保存程序→按固定版本制作目标平台升级包→通过批准渠道转入办公机→核对版本和文件清单→备份、停用、更新、接入、合成验证→启用。

纯程序升级包只带变化的程序、必要接入更新及发布清单；依赖或模型变更则另带相应离线包和兼容验证。新安装版本也可以并排放置后验证再切换，但必须说明入口及数据位置，不能制造一套未解释的新目录。

行内电脑不需要也不应为了升级而临时接通公网GitHub。现场遇到问题，记录版本、错误、脱敏说明或合成复现，经批准带回开发环境修复；不要把客户文档、数据库和原始会话传到公开仓库或公网模型。

## 9. Git、本地备份、GitHub和离线包的区别

| 项目 | 保存什么 | 不代替什么 |
|---|---|---|
| 本地Git提交 | 程序和文档的可比较版本 | 不保存被忽略的依赖、客户数据和运行配置 |
| GitHub推送 | 获准公开的Git历史及分支/标签 | 不是运行目录同步，也不是完整安装包 |
| 运行环境备份 | 指定版本程序、依赖和必要配置，用于现场恢复 | 不能自动替代一致性的业务数据库备份 |
| 离线发布包 | 目标平台可安装的程序与环境，以及验证/回退材料 | 不是把所有个人目录一起复制 |

目前GitHub维护入口是`improve/fill-efficiency`，`main`仍保留旧基线。下载默认main不能当成“已取得这次好成绩的最新维护版本”。本说明的快照标签为`toolv2-guide-plain-20260927`；它是程序/文档快照，不是目标办公机离线验收标签。旧的`toolv2-handoff-20260927`保留历史，不改写。

让DSH在代码开发树核对`git status`、分支、远端，选择明确文件提交，再普通推送功能分支，核对本地HEAD与远端提交一致。公开仓库不接收客户资料、密钥、数据库和会话；不强推，不为凑“干净”执行破坏性清理。若以后需要把维护分支合入main，应作为一次明确版本发布处理并验证，而不是暗中切换。
