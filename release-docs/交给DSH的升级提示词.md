# 给DSH的维护任务入口

新建一个DSH维护会话，选择干净的代码工作树，例如本机`D:\DSH-worktrees\fill-efficiency`；普通业务填表会话继续选业务资料目录，两者用途不同。直接粘贴下面内容，补充最后四项即可。无需同时粘贴全部历史聊天、源码或参考答案。

```text
这是toolV2软件维护任务。请先读本仓库AGENTS.md、toolV2/AGENTS.md、toolV2/MAINTENANCE.md和release-docs/maintenance-state.md，再按需求只读相关代码与测试。

先用不超过8行说明：现状证据、需要改变的行为、打算修改的模块、验收方法及确实缺少的信息。信息够就直接实施，不要停在方案，也不要让我重复确认来源里已有的信息。

沿用现有引擎、数据库和工作流；不要为本次样例写死客户、答案、模板名或金额，不清库、不绕过权限，不修改第三方依赖源码。旧模式保留，新场景明确自己的主体和数据范围。模型判断由程序校验与测试支撑，不能仅凭“看起来合理”宣布成功。

我授权本次需求范围内的开发、合成测试、本地Git提交和推送到现有GitHub仓库的功能分支。请在干净工作树和功能分支施工，检查待公开内容，普通推送后核对远端提交；不强推，不自动覆盖main。提交代码不等于已启用，日常运行版的启用范围以我下面的选择为准。

先最小复现/验收用例，再修改并运行相关检查；共享流程改变时执行回归。相同文件和配置未变化时，不反复读取和运行已通过的测试；失败先查原因，不用重复调用碰运气。不默认启动多代理；需要分工时明确文件范围，避免重复阅读和同时编辑。

最后简要报告实际改动、测试与输出证据、首次/复用耗时、提问次数、Git提交与远端状态、启用状态及仍不能证明的边界；更新maintenance-state.md供下一次继续。

本次只做的功能或缺陷：……
输入/输出及样例位置（开发模型测试用合成资料）：……
验收条件（可检查的数量、对应关系、保留格式等）：……
日常运行启用范围：默认先交付供复核；如我在此明确授权启用，请在验证和备份后执行，不再重复询问同一授权。
```

一次只给一个可验收增量。例如“先让3家合成企业各生成1份，核对企业和利率不串，再扩大到300家并测失败恢复”；不要在同一轮同时要求批量、产品合并、OCR和重新设计界面。

提示词帮助定义范围，但不能消除模型能力差异。是否达到要求，仍以版本、运行结果和独立测试判断；不能把“写了更长提示词”当作能力已经提高。
