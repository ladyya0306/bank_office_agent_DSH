# DSH与toolV2完整使用、维护、升级和离线部署说明

核对日期：2026-09-27。本文件替换此前不完整的“升级提示词”。先解释电脑上的实际目录，再讲怎么操作；最后才是可复制给DSH的任务文字。

先分清三个名字：**DSH是承载对话、模型和工具的应用；模型负责理解需求和不明确的字段关系；toolV2是DSH调用的办公填报工具流程。** 更新toolV2、升级DSH依赖、切换模型是三种不同变更，应分别验证。DSH可以协助修改toolV2，但普通填表会话不会自动升级共享程序。

## 1. 先回答最重要的四个问题

**你一直使用的是运行目录`D:\DSH`。** 在`D:\DSH\deepseek-harness-local`执行`npm start`，启动这个目录中的DSH，并接入它旁边的`D:\DSH\toolV2`。日常启动命令不用改。

**`D:\DSH-worktrees\fill-efficiency`是为修改程序另开的开发工作目录。** 当时为避免边修改边影响日常填表，维护代理创建了它；此前没有把这件事解释清楚。它不是另一套必须随产品安装的软件，也不是你测试时偷偷调用的替代引擎。

**开发目录的修改不会自动同步到运行目录。** 上轮是在开发目录完成修复和检查，再把通过检查的程序文件复制到`D:\DSH`并重新接入。你随后测试的是运行目录里已经更新的程序。这就是“在开发目录改过”与“你在运行目录使用”同时成立的原因。

**离线部署不带开发工作树，也不能把整个`D:\DSH`直接压缩交付。** 应按选定Git版本导出干净程序，补齐目标电脑适用的运行时、依赖和模型配置，做成离线发布包。包中不混入客户材料、数据库、旧会话或个人凭据。第7节给出具体组成。

## 3. 目录和文件分别负责什么

### 3.1 日常运行和业务资料

| 目录或文件 | 职责 | 日常如何处理 |
|---|---|---|
| `D:\DSH` | 本机程序安装与运行的总目录；历史上同时也是Git主工作目录 | 日常从这里启动，不把整个目录当作干净发布包 |
| `deepseek-harness-local/start.js` | 启动DSH、检查toolV2接入、输出启动日志 | 已验证升级才更换，不用于存业务资料 |
| `deepseek-harness-local/tool-v2-startup.cjs` | 找同级toolV2，调用它的接入程序 | 决定启动时寻找哪套toolV2 |
| `deepseek-harness-local/node_modules` | DSH及Node第三方依赖 | Git不保存；离线包需要另行准备兼容版本 |
| `deepseek-harness-local/package.json`、`package-lock.json` | 程序启动命令和依赖版本记录 | 不是依赖文件本身；离线机不能只靠它们安装 |
| `deepseek-harness-local/.env` | 本机运行及模型配置，可能含密钥 | 每台机器分别配置，不上传GitHub，不照搬个人凭据 |
| `deepseek-harness-local/workspace/profiles/web`、`hooks.json` | DSH工具、插件及Python路径的接入配置 | 移机或换候选版后使用现有接入程序核对，不凭记忆修改路径 |
| `workspace/plugins` | 批准、目录选择、填表等DSH插件 | 部分是版本化程序，部分由接入脚本生成；不能把整个workspace当依赖复制 |
| `workspace/skills/office-suite` | DSH实际加载的办公技能副本 | 原始技能在toolV2目录；只改这里可能被下次接入覆盖 |
| `workspace/sessions` | DSH对话、工具调用和交互记录 | 本地追查，不放公开Git或新机器的干净首装包 |
| `workspace/backups` | 接入脚本对旧配置、插件、技能的备份 | 不是完整程序备份，也不是业务数据库备份 |
| `deepseek-harness-local/logs` | 启动器运行日志；旧根目录日志也已归档到这里 | 不与业务数据库或会话记录混为一谈 |

| `D:\DSH\test B`，以及test A、test3等 | 独立业务或测试工作区 | 不是程序版本；切换业务目录不会自动切换引擎 |

## 5. 以后怎样让DSH修改功能

### 第一步：进入维护会话，而不是业务会话

DSH网页仍可由运行目录启动。另开一个会话，将会话目录选为`D:\DSH-worktrees\fill-efficiency`，把第10节的维护说明发给模型。这个选择只是允许模型在代码目录工作，**不代表网页中的`office_fill_task`已改用候选引擎**。

一次说明一个目标，例如“同一模板按企业输出多份”，并给合成样例与可检查的验收条件。无需重讲全部历史。

### 第二步：在功能分支修改，先验证候选代码

让DSH先核对分支、提交和未提交改动，再从当前维护版本新建功能分支。小改动可复用空闲开发工作树，不必每次增加一套目录。遇到未完成的其他改动，要保留并说明，不覆盖它们。

候选代码的测试应从开发树执行，例如：

```powershell
cd D:\DSH-worktrees\fill-efficiency
$env:PYTHONUTF8='1'
$env:PYTHONPATH=(Resolve-Path toolV2).Path
python -m pytest -q toolV2/tests
```

先跑相关测试；共享解析、确认、状态或写入器改动时再跑全量。只改文档则检查文档和链接，不反复跑无关测试。更细的命令见`toolV2/MAINTENANCE.md`。

### 第三步：需要网页端实测时，明确候选DSH实例

仅改变会话目录不够。候选DSH需有自己的接入配置、兼容依赖和批准的模型配置，接入的`toolRoot`必须指向候选`toolV2`。维护代理应完成这一步并报告实际路径，不能让你猜。

当前开发目录即使存在node_modules，也不代表以后每个新工作树都自带全部依赖。本轮核查时，该开发树尚缺profiles/web/cordis.patch.yml及hooks.json，直接npm start会失败。先检查并准备候选依赖与获准模型配置；不从运行目录整包复制包含会话、凭据的workspace。用已装好核心依赖的候选Python初始化接入配置：

```powershell
cd D:\DSH-worktrees\fill-efficiency
python scripts/prepare_checkout.py
```

核对脚本成功，且接入结果中的tool_root为`D:\DSH-worktrees\fill-efficiency\toolV2`。若Python不是PATH中的python，改用其完整路径运行脚本，并把同一路径设置为`DSH_OFFICE_PYTHON`，保证后续启动使用同一解释器。此步骤只准备接入，不下载依赖或配置模型。

在候选环境已准备完毕的前提下，可用独立端口运行，避免替换正在用的3080服务：

```powershell
cd D:\DSH-worktrees\fill-efficiency\deepseek-harness-local
$env:HOST='127.0.0.1'
$env:PORT='3081'
$env:WORKSPACE_DIR=(Join-Path (Get-Location) 'workspace')
npm start
```

候选网页用新的合成业务工作区测试，不拿正在使用的业务数据库试验。结束后退出该候选进程；这些环境变量只用于这个PowerShell窗口。该示例是操作方法，本轮没有为新功能另启动候选服务。

### 第四步：验证旧能力没有变差

保留旧模板的本地回归和无客户信息的合成变体，同时测新功能。至少比较：错填、漏填、主体是否串位、单位与格式、提问次数、首次生成/重复查询耗时、中断和单文件失败后能否继续。

例如300家企业功能，应验证企业标识和输出文件一一对应、利率不串户、失败重试不重做已成功文件。仅输出300个文件不算完成。陌生模板应与开发时反复调整的样例分开测试。

### 第五步：提交、推送，再决定是否启用

开发测试、保存Git、推送GitHub、复制到运行目录、重启接入、业务验收是不同动作，要分别报告。用户已经授权的步骤直接完成；没有启用授权时，先交付可复核结果再确认启用，不反复询问同一授权。

## 6. 本地升级和回退怎样做

本机路径保持`D:\DSH`即可，不用改你平时的启动习惯。

1. 记录已通过测试的Git提交、改动文件和依赖变化；确认没有正在执行的填表任务。
2. 保存受影响运行程序、接入配置、插件/技能的备份及文件清单。涉及数据库结构变化时，另做一致性数据库备份和迁移方案；代码备份不能代替数据库备份。
3. 退出旧DSH进程。只更新本次批准的程序和必要依赖，不把开发数据库、个人.env、会话或客户材料复制进去。
4. 用目标运行环境的Python执行运行目录中的接入程序，核对返回`tool_root`及Python路径，再按原命令启动。
5. 先跑独立合成工作区验证，再交付业务使用。记录实际启用提交、文件校验值、时间及备份位置。

接入命令示例，`python`必须指向本机实际可用且装好办公依赖的解释器：

```powershell
python D:\DSH\toolV2\install.py --dsh-root D:\DSH\deepseek-harness-local
```

**回退不是清库。** 停止新进程后，恢复上一个版本的程序、匹配依赖与接入配置，核对路径后启动。保留业务原件、数据库和产物。若数据库已经迁移，新旧代码是否兼容必须先判断；不兼容时按事先准备的数据恢复方案处理，不能直接拿旧库覆盖今天新增的业务记录。

Git标签能找到旧源码，但不会替你恢复运行目录、node_modules、Python库或数据库。`install.py`会备份部分接入配置，尚未实现失败后自动回滚。当前也没有一键离线发布、升级和数据库回退工具，不把上述人工维护步骤说成现成功能。

## 7. 离线安装包到底取哪里、装什么

### 7.1 打包来源

**源码取选定Git提交或标签；运行依赖从已经验证的环境准备，并匹配目标电脑。** 本机`D:\DSH`用于核对“好成绩所用程序”和依赖，不作为可整包公开分发的材料目录。开发工作树用于导出干净源码，不作为另一台电脑的运行依赖。

不复制`D:\DSH-worktrees`，不复制其中指回本机的`.git`文件，也不把`D:\DSH\.git`放进面向业务使用者的安装包。目标电脑正常使用DSH不要求装Git，更不要求能访问GitHub。

例如，在有该标签的开发仓库导出固定源码（先创建下面的输出目录；这是制作包时的命令，本轮未执行打包）：

```powershell
git -C D:\DSH-worktrees\fill-efficiency archive --format=zip --output=D:\DSH-release\toolv2-guide-20260927-source.zip toolv2-guide-20260927
```

这个ZIP只含Git保存的文件，不含node_modules、Python或模型；继续补齐下表内容并验证后，才是可交付的离线包。如此取到的是明确版本，而不是开发树里尚未提交的试验改动。

### 7.2 一个完整首装包应包含什么

以下是发布包规划，**目前尚未制作并在目标办公机验收这样的完整离线包**。

| 组成 | 内容 |
|---|---|
| 程序 | 固定版本的toolV2、DSH启动器、已跟踪的本地插件、技能源、准备/接入脚本和说明 |
| Node运行环境 | 经目标系统验证的Node安装包或运行时，以及该平台适用的DSH/node_modules依赖 |
| Python运行环境 | 经目标系统验证的Python安装包、核心依赖及其依赖包；通常准备离线wheel包集合 |
| 可选能力依赖 | 实际启用的PDF、OCR等能力所需库与资源，单独列明；安装了不代表已经验收 |
| 模型 | 目标机允许的本地模型运行时、权重与配置，或获准内网服务配置；不是复制个人API密钥 |
| 发布证据 | Git提交/标签、平台与架构、运行时/依赖/模型版本、文件SHA-256清单、合成样例及验证结果、安装和回退步骤 |

本机的Python当前来自Windows用户目录中的安装环境，不能把`D:\DSH`压缩就认为Python也已带走；现有虚拟环境也不宜原样跨机搬运。requirements文件是版本声明，不是离线依赖包。`install.py`只检查/接入，不替你安装这些依赖。

Node版本也有待发布前统一的事项：历史实测记录为22.18.0，而package.json声明至少22.19.0。应选择并验证满足项目要求的固定版本，不能把这个差异略过或笼统“下载最新版”。Windows和UOS/Linux、不同CPU架构的运行时及二进制依赖应分别准备；不要把Windows的node_modules或Python轮子直接当UOS包。

### 7.3 明确排除的内容

不打包本机`.env`、密钥、客户source/target/in/out、业务db、DSH会话、日志、备份、audit_work、test A/test B/test3、个人工作区状态。需要延续旧业务时，另做批准的数据迁移包，不能混进程序首装包。

`workspace`不能全部复制或全部丢弃：版本化插件是程序，需要随版本提供；profiles/hooks可由`prepare_checkout.py`和`install.py`生成接入；sessions、日志、运行状态和凭据属于本机数据。`office-tool-v2`插件和办公技能副本可从toolV2源目录重建；已禁用的旧插件不应被当作新包的隐含依赖。

业务资料目录由用户另选，不必放在安装根目录；不能假设换了电脑仍存在原来的C盘用户路径。

下面是Windows离线首装的操作示例，假设批准包位于`E:\DSH-offline`、程序已放到`D:\DSH`，兼容的Node/Python已安装且PATH已核对。E盘只是示例，不是本机已制作好的包：

## 8. 后续怎样离线升级行内电脑

开发机维护并测试→本地Git提交→推送获准GitHub分支保存程序→按固定版本制作目标平台升级包→通过批准渠道转入办公机→核对版本和文件清单→备份、停用、更新、接入、合成验证→启用。

纯程序升级包只带变化的程序、必要接入更新及发布清单；依赖或模型变更则另带相应离线包和兼容验证。新安装版本也可以并排放置后验证再切换，但必须说明入口及数据位置，不能制造一套未解释的新目录。

行内电脑不需要也不应为了升级而临时接通公网GitHub。现场遇到问题，记录版本、错误、脱敏说明或合成复现，经批准带回开发环境修复；不要把客户文档、数据库和原始会话传到公开仓库或公网模型。

## 9. Git、本地备份、GitHub和离线包的区别

| 项目 | 保存什么 | 不代替什么 |
|---|---|---|
| 本地Git提交 | 程序和文档的可比较版本 | 不保存被忽略的依赖、客户数据和运行配置 |
| GitHub推送 | 获准公开的Git历史及分支/标签 | 不是运行目录同步，也不是完整安装包 |
| 运行环境备份 | 指定版本程序、依赖和必要配置，用于现场恢复 | 不能自动替代一致性的业务数据库备份 |
| 离线发布包 | 目标平台可安装的程序与环境，以及验证/回退材料 | 不是把所有个人目录一起复制 |

目前GitHub维护入口是`improve/fill-efficiency`，`main`仍保留旧基线。下载默认main不能当成“已取得这次好成绩的最新维护版本”。本说明的快照标签为`toolv2-guide-20260927`；它是程序/文档快照，不是目标办公机离线验收标签。旧的`toolv2-handoff-20260927`保留历史，不改写。

让DSH在代码开发树核对`git status`、分支、远端，选择明确文件提交，再普通推送功能分支，核对本地HEAD与远端提交一致。公开仓库不接收客户资料、密钥、数据库和会话；不强推，不为凑“干净”执行破坏性清理。若以后需要把维护分支合入main，应作为一次明确版本发布处理并验证，而不是暗中切换。
