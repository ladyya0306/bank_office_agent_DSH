## 现在能做与尚不能承诺的事

| 场景 | 当前边界 | 缺少什么 |
|---|---|---|
| 一个借款业务涉及借款人、保证人及多份Word/Excel模板 | 已在15份真实模板验证主体关系、填值、必要确认、恢复和格式修复；当前业务默认与借款场景相关 | 不等于每一空白都可自动识别；无来源、冲突和不适用位置仍需说明或确认 |
| 陌生DOCX/XLSX，版式完全不同 | 有通用位置发现及模型补充映射机制，并非只能处理那15个文件；仍可能漏识别、错配或需要补充映射 | 独立陌生版式测试、按失败类型补充解析和格式校验；不能承诺零提问、全自动或157秒 |
| 300家企业明细，同一模板生成300份 | **现有`office_fill_task`尚未实现这项批量语义**；目前任务主要按模板文件生成结果 | 按企业唯一标识分组、每份文件限定一家企业的资料、300份输出清单与数量/串户校验、失败续做；不能把300家混在一个事实范围内当作已支持 |
| 以产品为主体，合并A/B/C的特征 | 能读取多个来源并提示部分同字段冲突；**产品识别、跨文件关联和特征合并流程尚未完成** | 产品标识、适用时间/版本、每个特征的出处和冲突处理；不能让借款人默认规则承担产品归属 |
| PDF文字或扫描件作为来源 | 底层有PDF提取及本地OCR工具；**尚未接通`office_fill_task`的自动来源处理** | 文字PDF与扫描件分流、OCR依赖和质量验证、页码及证据保留、低可信识别复核；安装了OCR工具不等于端到端已通过 |

代码依据：`workflow/runner.py` 按目标模板建立和执行计划；`workflow/source.py` 合并来源并处理归属；`office_kit/absorb.py` 当前直接来源格式不含PDF；`office_kit/cli.py` 提供底层extract/ocr入口；`office_kit/ocr_ops.py` 使用可选OCR依赖。底层命令存在与工作流已接通是两件事。

## 如何扩展，如何避免原有能力变差

建议在toolV2上增量建设，复用现有Word/Excel读写、证据、冲突确认及恢复机制；现阶段没有依据推倒重做。未来新增“逐企业套模板”和“产品资料合并”等明确任务模式，各自定义主体与输入范围；PDF/OCR作为来源读取扩展。不要把所有新需求塞进借款人/保证人的默认判断。

修改共享代码确实可能让旧能力变差，不能保证绝不退化。保留`1c4fb80`作为对照及回退点；每项增量同时跑原15模板的本地回归、无客户信息的合成变体和新模式测试，比较正确性、格式、提问、耗时及token。只更新变化的部分；不能为追求新功能而删掉原测试或把预期结果改成错误输出。上述扩展是建议，本轮没有实现300份生成、产品合并或OCR接入。
