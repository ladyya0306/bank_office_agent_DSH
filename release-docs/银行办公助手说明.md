# 银行办公助手说明

## 做什么

银行办公助手（toolV2）把一批源资料整理成可供复核的 Word（.docx）和 Excel（.xlsx）目标文件。它复用已有办公读写能力，并增加按任务连续执行、用户确认、重复任务恢复和逐文件结果记录。

当前适用范围是工作区内的资料与目标文件。目标支持 Word 和 Excel。源资料主要按可识别的“标签：值”内容提取；它不是通用扫描识别器，也不保证适配所有合同、图片和模板。

## 用户如何审核

一次填表涉及三个不同环节：

1. **操作批准**：DSH 按本机设置询问是否允许工具执行。选择“本会话同类操作一直允许”只影响工具操作的批准提示，不代表确认了资料值，也不代表业务签核。
2. **资料与填写内容确认**：工具将无法确定归属、相互冲突或需要确认的内容列成原生卡片。卡片显示材料出处、原文、建议主体及理由。用户可以选择建议、暂不收录、留空或填写自定义内容。相同字段要写入多份目标文件时，会合并问题并列出所有位置。位置不明确的新模板会先停止并返回需确认的位置清单，按清单修正规则后再继续。
3. **最终人工复核**：输出完成后，用户逐份检查字段、位置、留空项和业务含义，并按业务流程决定是否签核。完成填表不表示已经签核，工具不替用户签名。

回答由 DSH 原生提问界面收集，再由程序写入所选工作区的 SQLite 数据库。取消或中断时可用原 task_id 恢复；源材料或目标位置有变化时，程序会重新核对受影响的内容。

### 合成示例

> 示例源材料原文：“借款企业名称：示例企业甲；借款期限：24个月。”
>
> 确认卡片：“填写位置：授信申请表（基本信息表，企业名称后）。建议填写：示例企业甲。选项：采用建议值、留空；也可输入自定义内容。”
>
> 这是合成示例，不对应真实客户、账号或业务。

## 日志在哪里，如何查看

有两类记录，另有一份任务结果报告：

- **DSH 会话记录**：在 DSH 会话时间线查看工具调用、工具结果和原生操作批准卡片。维护人员也可在 DSH 仓库根目录执行以下命令查看批准记录：node scripts/show_approvals.mjs --session "会话目录或压缩日志文件"。底层会话记录通常位于 DSH 数据目录的 workspace/sessions/<会话目录>/<会话ID>/session.v3.jsonl.zstd，文件可能经过 zstd 压缩。用会话中的 task_id 对照工具输入与返回结果。会话记录帮助还原对话和工具操作，不等同于办公数据库中的业务事实记录。
- **办公数据库**：位于本次选定办公工作区的 db/workflow.db。维护人员可在 DSH 仓库根目录只读查询，例如：python scripts/read_office_db.py --work "业务工作区" --section tasks --limit 10。可选 section 为 tasks、facts、answers、outputs、events、rules。命令以只读方式打开数据库并输出 JSON；其中事实、答案等结果可能含有敏感数据，只能在受控环境查看。数据表包括：office_v2_task、office_v2_cache 保存任务和解析缓存；source 登记源文件；fact 保存提取事实；fact_conflict 保存冲突；template、template_rule 保存模板及位置规则；fill_op 保存办公引擎执行与产物记录。具体需查什么再选对应 section，避免输出不必要的业务值。
- **任务报告**：填写程序通常将 Markdown 汇总报告写到工作区 out/<批次>/_报告/，目标文件写在 out/<批次>/ 下的相应目录。报告列出处理状态、填写数、留空和未签核提示。报告不是签核凭证，也不能证明所有视觉空白或业务字段均已检查。

不要把工作数据库、源资料、目标文件、DSH 会话记录或密钥上传到公开仓库。也不要在查看时运行写库命令或直接修改数据库。

## 怎样按任务和批次追溯

- 一次任务有 task_id；同一工作区、同一批次、同一组源文件和目标文件可用它恢复。
- 批次格式为 YYYYMMDD-NN，用于区分业务批次。不要用客户名称等敏感信息作为批次标记。
- 数据库任务表记录任务状态与逐文件处理结果；fill_op 以 run_id、batch_no、文件产物路径及产物哈希关联执行记录。结果报告按批次放在输出目录。
- 源资料变化、模板变化或填写位置变化后，应恢复原任务并检查工具重新提出的确认项。用户也可以对照源文件、目标原件、输出文件和数据库中的文件哈希进行人工核对。
- 哈希只能用于比较文件内容是否一致，不能证明操作者身份、记录真实性或文件未被有权限者改写。

本次复核将16份数据库登记的产物哈希逐一与文件比较，16份均相符。这说明已登记产物与数据库中的哈希一致，但不能单独证明每一步修改均由办公工具执行。若发生绕过工具直接修改的情况，该改动未必进入办公数据库；最终核对仍应对照会话记录、数据库、原件和实际输出。

## 当前验证与限制

截至2026年9月25日，代码和合成资料检查覆盖了固定任务流程、重复调用与恢复、源文件变化、批次区分、目标位置映射和 Word/Excel 写入等场景。另以15份真实模板副本测试了267个已识别的非保护填写位置，统一使用模拟值123；记录为0项校验错误、0项写入错误，未修改生产数据库或在线模板。这说明这些测试位置的写入与读取检查通过，不证明123是业务正确值，也不证明模板内所有字段均已验证。

按使用者报告，15份目标文档在一次验收中用时12分57秒。该次工具结果为15份文档完成（其中1份为留空副本）、60个填写位置、0份失败。另核对的16份数据库登记产物，其哈希均与数据库记录相符。时间和数量均为这一次记录，不能当作普遍性能或字段正确率。复核仍发现两处语义问题：Excel标签格与右侧填写格出现重复；“期限___年”位置填入了日期区间。这说明任务状态为完成、执行失败数为0和产物哈希相符，都不能证明业务含义完全正确。使用者仍应逐份检查并决定是否签核。

目前没有银行认证或不可篡改审计能力的证明；哈希链或文件哈希不构成防篡改承诺。此处描述的是本地 Windows 开发环境和本地工具/合成数据验证，不代表办公电脑已断网实测，也不代表本工具可在无网络、无模型服务的电脑上独立完成任务。离线部署是后续方向，需在目标办公环境核对模型服务、依赖、访问控制、日志留存和数据边界。

互联网模型与行内模型的使用条件不能混为一谈：互联网模型只可处理按本行要求允许外发的数据；行内模型也须经过本行准入、部署、权限和数据管理要求，不能仅因部署在行内就默认获准。公开代码仓库只应放程序与脱敏文档，不上传工作区 SQLite 数据库、源资料、目标文件、DSH 会话记录或密钥。
